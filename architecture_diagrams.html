UbeU System Architecture

Figure 1. High-Level Layered Architecture

Figure 1. UbeU's layered architecture (bottom-up). The scenario contract (L1) defines behavioral invariants that all upper layers enforce. Each layer reads from and writes to the shared state plane (L2). Layers stack without direct coupling — any layer can be tested, swapped, or extended independently.

L1 — Scenario Contract (foundation)
The SimulationScript defines everything the simulation needs before it runs: who the stakeholders are (with OCEAN personality priors, incentives, and concerns), what phases the conversation follows, what actions are allowed, how actions change world state (transition rules), and what external events occur. This is the behavioral contract — every layer above enforces its constraints.

L2 — State Plane (single source of truth)
The Simulation State Ledger stores all runtime state in one place: the full dialogue transcript, each actor's commitments and whether they've been fulfilled or contradicted, relationship edges between actors, rolling personality trait estimates and drift measurements, world state snapshots, and all action proposals with their execution status. Every other layer reads from and writes to this ledger. It is not convenience memory — it is a reproducibility contract that prevents the simulation from "forgetting" critical constraints across turns.

L3 — Action Layer (separating saying from doing)
Extracts structured actions from dialogue text (e.g., "I'll take ownership of the budget review" becomes an assign_owner action), validates them against the scenario's action ontology, arbitrates competing actions at phase boundaries (e.g., two actors claiming the same task), applies the resulting state deltas to world state, and feeds execution outcomes back into the next phase's context.

L4 — Generation Plane + Persona Control Plane (producing faithful dialogue)
These two work in tandem every turn. The Generation Plane (Stakeholder Actor) first creates a policy plan for the turn, then generates 4-5 candidate responses across distinct style slots (integrator, planner, challenger, skeptic), each with a rotated action vocabulary to prevent mode collapse. The Persona Control Plane (PersonaStateController) scores every candidate against 8 criteria — identity consistency, OCEAN drift bounds, commitment continuity, relationship consistency, adequacy, sycophancy risk, action plan alignment, and diversity contribution — then selects the best one. If drift exceeds the target band, it injects a corrective nudge into the next turn's prompt. No regeneration is needed; the controller picks from what's already been generated.

L5 — Runtime Control Plane (orchestration)
The LangGraph-based orchestrator runs the simulation loop: scheduling phases (OPENING → TENSION → NEGOTIATION → CLOSING), injecting world events at the right moments, cycling through actors in round-robin order, checkpointing after every run for crash recovery, and coordinating the handoff between generation, control, and action layers each turn.

L6 — Evaluation + Reporting Plane (output)
The Evaluation Plane independently validates simulation results using a deterministic 30-feature behavioral scorer (the same one that runs at runtime) plus a cross-provider multi-model jury with dual-order prompting and uncertainty-triggered escalation. The Reporting Plane aggregates metrics (drift MAE, contradiction rate, envelope violations, trajectory variance, per-trait errors) and produces audit-ready artifacts — every actor utterance is traceable back to its candidate pool, scoring rationale, and state context.

Figure 2. Simulation Runtime Loop (Per-Phase)

Figure 2. Per-phase simulation loop. The left section shows the per-turn cycle; the right section shows what happens when a phase ends. The "Next Turn" path returns to the next actor in round-robin order.

The simulation runs as two nested loops: an outer phase loop and an inner turn loop.

Outer loop — Phase progression: The simulation moves through four phases in order: OPENING (surface each stakeholder's initial position), TENSION (expose conflicts and tradeoffs), NEGOTIATION (search for compromises), and CLOSING (summarize commitments and unresolved issues). Each phase has a fixed maximum number of turns. When all turns in a phase are exhausted, the phase-end sequence fires before moving to the next phase.

Inner loop — Per-turn cycle (7 steps):

  1. Inject World Events — If the scenario script has an event triggered for this phase (e.g., "new budget data arrives"), it gets injected into the shared context so all actors can see it.
  2. Prepare Actor Context — The runtime assembles a context window for the current actor: recent dialogue turns, their personality profile, active commitments, relationship state with other actors, and relevant world state values.
  3. Generate Policy Plan — The actor's LLM generates a structured plan for this turn: what position to take, what information to surface, and what action to consider. This plan guides candidate generation but doesn't lock in a specific response.
  4. Generate Candidate Pool — The actor generates 4-5 candidate responses, each through a different style slot (integrator, planner, challenger, skeptic). Each slot uses a rotated action vocabulary so the candidates are genuinely different, not minor rewrites of the same idea.
  5. Score & Select — The PersonaStateController scores all candidates against 8 criteria (identity consistency, OCEAN drift bounds, commitment continuity, relationship consistency, adequacy, sycophancy risk, action plan alignment, diversity contribution) and selects the highest-scoring one. If drift exceeds the threshold, a Nudge is prepared for the next turn's prompt.
  6. Commit Turn — The selected utterance is appended to the ledger. The ledger updates trait estimates, extracts any new commitments from the text, and updates relationship signals.
  7. Propose Action — The action layer extracts a structured action from the dialogue text (e.g., "assign_owner", "request_evidence") and registers it as a proposal for phase-end arbitration.

After the last turn in a phase, the Phase End sequence runs:

  1. Arbitrate Actions — All action proposals from this phase are validated against the ontology and checked for conflicts (e.g., two actors claiming ownership of the same task). Valid proposals are approved; invalid ones are rejected with a reason.
  2. Apply State Transitions — Approved actions trigger state deltas defined in the scenario's transition rules (e.g., an "assign_owner" action increases execution_confidence by 0.08 and alignment by 0.04).
  3. Resolve Commitments — Commitments made during this phase are checked: fulfilled ones are marked complete, stale ones are resolved, and any contradictions are flagged.
  4. Summarize Feedback — A phase summary is generated and fed into the next phase's context, so actors know what was decided and what remains unresolved.

Figure 3. User Workflow

Figure 3. End-to-end user workflow. Each stage's output feeds the next; full-chain traceability is preserved from brief to final report.

1. Brief Input — The user describes a decision scenario in plain language: who the stakeholders are, what the decision is about, and what tensions exist. For example: "A hospital is deciding whether to adopt AI-assisted diagnostics. The chief of medicine is cautious about liability, the radiology department head wants it for efficiency, and the patient advocacy group has concerns about consent and accuracy."

2. Script Generation — An LLM generates a structured simulation script from the brief: stakeholder specs with OCEAN personality priors, phase definitions, world events, allowed action types, and transition rules. The builder enrichment layer then normalizes the output — filling in missing fields from scenario family templates, validating action ontology references, and generating actor-specific action preferences. The result is a complete SimulationScript that conforms to the behavioral contract.

3. Simulation Execution — The runtime executes the script through the full phase loop (Figure 2). Each turn produces a persona-controlled utterance with a scored candidate audit trail. Actions are proposed, arbitrated, and executed. The state ledger records everything: dialogue, commitments, relationships, trait estimates, world state changes, and action traces.

4. Evaluation — After the simulation completes, the evaluation plane independently validates behavioral fidelity. The deterministic scorer extracts 30 behavioral features from the transcript and computes per-trait OCEAN scores. The multi-model jury (5 providers) scores the same traits with dual-order prompting to control for position bias. When the two tracks disagree beyond a threshold, escalation triggers a deeper review. This dual-track design catches both systematic LLM biases and edge cases the deterministic scorer might miss.

5. Analysis & Report — Metrics are aggregated across runs: persona drift MAE, per-trait errors, commitment contradiction rate, relationship inconsistency, envelope violations, action family convergence, role-action diversity, and state trajectory variance. The report includes per-scenario breakdowns, per-actor trait trajectories, and full audit artifacts — every utterance is traceable back to its candidate pool, scoring rationale, policy plan, and state context at the moment of generation.

Figure 4. Persona State Controller — Score & Select Detail

Figure 4. Persona State Controller detail. Left: style-diverse candidate pool. Center: multi-criteria scoring. Right: three outputs per turn — the selected utterance, an optional drift nudge, and a full audit log.

This is the core mechanism that makes UbeU's persona fidelity possible. It operates every turn, between candidate generation and turn commitment. The diagram reads left to right in three stages:

Stage 1 — Candidate Pool (left)
The Stakeholder Actor generates 4-5 candidate responses, each through a different style slot. An integrator slot produces a response that seeks common ground; a planner slot focuses on next steps and structure; a challenger slot raises objections and counterarguments; a skeptic slot questions assumptions and asks for evidence. Each slot also uses a rotated action vocabulary — the set of action types the candidate is encouraged to consider differs across slots. This prevents the common failure mode where all candidates say essentially the same thing in slightly different words.

Stage 2 — Scoring Criteria (center)
Every candidate is scored against 8 criteria simultaneously:

  • Identity consistency — Does the response sound like this specific actor (role, tone, domain expertise)?
  • OCEAN drift bounds — Does the response keep the actor's inferred personality traits within the target band? A high-Extraversion actor shouldn't suddenly become passive; a low-Agreeableness actor shouldn't suddenly agree with everyone.
  • Commitment continuity — Does the response honor or explicitly revise prior commitments, rather than silently contradicting them?
  • Relationship consistency — Does the response reflect the actor's established trust/tension relationships with other actors?
  • Adequacy — Is the response relevant to the current phase goal and conversation topic?
  • Sycophancy risk — Does the response show excessive agreement or deference to other actors, especially when the actor's personality and incentives suggest they should push back?
  • Action plan alignment — Does the response's implied action match the policy plan generated earlier for this turn?
  • Diversity contribution — Does the response add something new to the conversation, or does it repeat what others have already said?

Stage 3 — Outputs (right)
The controller produces three outputs:

  • Selected Utterance — The highest-scoring candidate becomes the actor's turn. No regeneration is needed; the controller picks from what's already been generated.
  • Drift Nudge (conditional) — If the drift check finds that the actor's rolling trait estimate has deviated beyond the target band, a soft corrective nudge is prepared. This is injected into the actor's next turn prompt as "Your prior positions: [list]" — just a factual reminder, not an instruction to behave differently. This approach was empirically tested: stronger instructions ("stay consistent unless explicitly revising") killed diversity, while this soft listing maintained zero contradiction without suppressing behavioral range.
  • Audit Log — Every selection decision is fully logged: all candidate texts, per-criterion scores for each candidate, the winning candidate's rationale, the current drift measurement, inferred traits at this point, and whether a nudge was applied. This is what enables post-hoc traceability — you can trace any actor utterance back to why it was chosen over the alternatives.
